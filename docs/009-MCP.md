# 009 — MCP Integration

## Status

Draft — Phase 3 (Architecture)

## 1. Why MCP, Not Bespoke Integrations

Every external system an agent touches — Git, a database, a browser, a cloud CLI — is reached through an MCP server, never a hand-rolled SDK call inside agent code ([[005-Agents]] §8). This is what makes new tools additive: a new MCP server plus a permission-grant is the whole change, no agent code is touched. This is also the concrete mechanism behind the "Plugin-based architecture" principle in [[000-Vision]] §5 for anything that's fundamentally a *tool call* rather than a full [[010-Plugins]]-style provider swap (Git provider, deployment target) — MCP and the Plugin System solve related but distinct problems: MCP standardizes *how* an agent calls a tool, Plugins standardize *which concrete provider* backs a capability like "the Git provider" or "the deployment target."

## 2. MCP Servers at v1

| Server | Used by | Scope |
|---|---|---|
| **Git / GitHub** | Developer, Git agents | Worktree/branch operations locally; push + PR creation against GitHub specifically, per [[ADR-0002]]. |
| **Filesystem** | Developer agent | Read/write scoped to the agent's current Worktree path only ([[007-ExecutionEngine]] §3) — never the Worker's home directory or another task's worktree. |
| **Terminal** | Developer, Deploy agents | Build/test commands (Developer), publish/migration/restart commands (Deploy) — scoped per [[014-Security]]'s permission boundaries (not repeated here). |
| **Web fetch/search** | Planner agent | Investigating a task's context beyond the repository itself, per [[000-Vision]] UC-3. |

## 3. Deferred to Phase 2 (Not MVP)

- **Azure DevOps** — the founder's original scope explicitly wanted Planner access to "abrir o devops, chamar o azure cli." Deferred per [[ADR-0002]] (GitHub-first), not dropped. Becomes the second Git/issue-tracker MCP server, and doubles as the acceptance test that nothing in this document's tool-permission model was accidentally GitHub-specific.
- **`az cli`** — same deferral, same reasoning; only relevant once a project's context genuinely lives partly in Azure.
- **Browser (Playwright)** — useful for the Planner investigating a live site/staging environment per the founder's original scope, not required for the first end-to-end pipeline validation, so sequenced after the MVP proves out.

## 4. Tool Permission Model

Which MCP tools a given agent role may call is fixed per role (not per task, not user-configurable at v1) and matches [[005-Agents]]'s per-role tool lists exactly — Planner never gets Git write access, Prioritizer never gets filesystem or terminal access at all (it only reads task data through the Forge API's internal service layer, per [[005-Agents]] §3), Deploy's terminal access is scoped to publish-related commands rather than the same generic terminal the Developer agent gets. This mapping lives in code as a static table (agent role → allowed MCP servers), not a database-configurable permission system — there is no product requirement yet for a project to grant a role *more* than its designed scope, and adding that flexibility before it's asked for would be speculative.

## 5. Error Handling and Timeouts

An MCP tool call failure is just another activity-level failure for Temporal's retry policy to handle ([[006-Scheduler]] §3, [[004-Workflow]] §4) — there is no separate MCP-specific retry layer. The distinction that matters is the same one [[004-Workflow]] already draws: a transient tool failure (timeout, rate limit) retries silently; a tool being genuinely unavailable or misconfigured should surface through the same domain-visible failure paths each agent role already has (`PlannerNeedsClarification`, `DeveloperNeedsClarification`, `DeployFailed`) rather than exhausting retries into an unexplained dead end.
