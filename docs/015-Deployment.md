## 1. Forge's Own Deployment Topology

Dedicated Linux server/VM isolated from Actiz's QA/PROD/PROD-LATIN clusters, per [[ADR-0004]]. **Currently substituted by the founder's local machine** (the amendment in that ADR) — all 6 services (Postgres, Temporal, Temporal UI, Forge API, Forge Worker, Frontend) run via the single root `docker-compose.yml`, unblocking architecture and code validation before the real server exists. This is scaffolding for validation only, not the target topology — when the real server is provisioned, the same container shape moves there per [[002-Architecture]] §4. See §6 below for the one-command bring-up and what's still specific to a given machine even in this containerized shape.

## 2. The PublishRecipe Gap, Resolved

[[005-Agents]] §5 and [[016-Roadmap]] both flagged the same open question: how does Forge know *how* to publish a given project locally? This document proposes a concrete answer rather than leaving it open indefinitely.

```
PublishRecipe {
  ProjectId: Guid
  MigrationCommand?: string   // e.g. "dotnet ef database update", run first if present
  RestartTargets: string[]    // shell commands to run in order after MigrationCommand -
                              // NOT bare service names (see the finding below)
  HealthCheckUrl?: string     // polled after restart; DeployCompleted only fires once it responds
  PreviewUrl?: string         // opened by the founder-requested "Testar" button once a
                              // task reaches Review - purely informational, never read
                              // by DeployAsync itself, see below
}
```

**Implemented** (not just proposed): stored as a JSONB column, `Project.PublishRecipe`, matching `Plugin.Configuration`'s pattern rather than an EF owned type — schema can grow without a migration each time. **All three of `migrationCommand`, `restartTargets`, and `healthCheckUrl` are executed by `AgentActivities.DeployAsync`** (founder-requested completion of the recipe): `migrationCommand` runs first if set, then each `restartTargets` entry runs as its own shell command in order, then `healthCheckUrl` is polled (up to 10 attempts, 3s apart, ~30s total) before `DeployCompleted` fires. Any step failing (migration, a restart, or the health check never turning healthy) produces `DeployFailed` and stops there — later steps don't run over a failed earlier one.

**`restartTargets` semantics changed, found live while dogfooding Forge on itself**: originally documented as bare Docker Compose service names (`docker compose restart {target}` assumed implicitly). The first real project to configure `restartTargets` was Forge itself — and Forge's own dev processes run as plain `dotnet run`/`vite`, not Compose services, so that assumption didn't fit. Each entry is now a **raw shell command**, run as-is (`RunShellAsync(runDirectory, command)`, no wrapping). A Compose-based project just writes `"docker compose restart api"` as the command instead of bare `"api"` — strictly more flexible, and no project had `restartTargets` configured before this change, so there was nothing to migrate.

**Validated live against Forge's own self-hosted restart**: `scripts/restart-forge-dev.sh` is the `Forge` project's `restartTargets` entry (a single command: `bash /home/felippe/repos/Forge/scripts/restart-forge-dev.sh`). It kills and relaunches Forge.Api and the Vite frontend, fully detached (`setsid nohup ... & disown`) so they survive after the script itself returns. **Deliberately never touches Forge.Worker** — that process is what's *executing* the Deploy activity calling this script; killing it would kill the activity mid-run, before it could report success or run the health check. A task that changes `Forge.Workflows`/`Forge.Worker` code still needs a manual Worker restart after review - a real, currently-unclosed gap of self-hosting, not hidden here. Tested directly (outside the full pipeline first): Forge.Worker's PID was confirmed unchanged after the script ran; Forge.Api and the frontend got fresh PIDs; `GET /health` (see below) returned `200` afterward.

**`GET /health` added, found necessary live**: adding global JWT auth (`ADR-0006`) meant any `healthCheckUrl` pointing at Forge's own API would always read as unhealthy (`401`, not `200`) the moment auth shipped. `/health` is `AllowAnonymous`, returns a bare `{"status":"healthy"}` - deliberately tells nothing about the system beyond "the API process is up."

**`previewUrl` is now backed by the same gate that makes `restartTargets`/`healthCheckUrl` trustworthy**, not just a plain human-maintained pointer as originally shipped: since Deploy now actually restarts the service and polls its health before completing, a task that reaches `Review` with a `previewUrl` configured genuinely has a freshly-restarted, health-checked build behind it — assuming the recipe's `restartTargets` are configured for that project. If a project's recipe has no `restartTargets` (or none configured at all), `previewUrl` is exactly as trustworthy as before: a plain pointer, accurate only if something external keeps it current.

**Gated on `Project.AllowAgentBypassPermissions`** (founder-requested trust flag, [[013-Frontend]]/[[016-Roadmap]]): `migrationCommand` and `restartTargets` both execute arbitrary shell commands unattended, the same risk class as the Developer agent editing files — so Deploy refuses with `DeployFailed` for any project not explicitly marked trusted, rather than running shell commands against an untrusted project by default. `healthCheckUrl` polling alone (no migration, no restarts) doesn't execute anything and isn't gated.

**Bug found and fixed while wiring this in**: the `PATCH /projects/{id}/publish-recipe` handler ([[012-API]]) called `JsonSerializer.Serialize(request)` directly, bypassing the API's configured camelCase JSON options (that configuration only applies to the framework's own request/response pipeline, not a manual serializer call) — it silently wrote `PascalCase` keys (`"PreviewUrl"`) into the stored JSON. `AgentActivities.PublishRecipeDto` tolerated it (case-insensitive deserialization), but the frontend's plain `JSON.parse` didn't, so a saved `previewUrl` read back as `undefined`. Fixed by passing `JsonNamingPolicy.CamelCase` explicitly at that one call site.

**Idempotency is the recipe author's responsibility, not something Forge enforces.** [[006-Scheduler]] §3 already caps Deploy activity retries at 2 attempts specifically because a partially-applied deploy shouldn't be retried blindly — but if a project's `MigrationCommand` isn't itself safe to run twice, that's a property of how that project's migrations are written, not something the Deploy agent can guarantee generically.

**Cleanliness is also the recipe author's responsibility — found live, not theorized.** A `migrationCommand` of `python3 -m py_compile calculator.py` left a `__pycache__/` directory behind in the worktree. That's an untracked file, so the Git agent's worktree removal ([[005-Agents]] §6) correctly *refused* to delete it afterward (`git worktree remove` without `--force`) rather than silently discarding it — exactly the safety behavior [[007-ExecutionEngine]] §2 and the project's `.claude/settings.json` "ask" list intend. The task still completed successfully (PR opened); only the worktree directory was left for manual cleanup. A recipe that produces artifacts should clean up after itself (or the project's `.gitignore` should exclude them) — Forge won't force-delete on a recipe author's behalf.

## 3. Deploy Agent's Publish Protocol

`migrationCommand` (if set) runs inside the **task's Worktree** (the branch under review — not the canonical clone, since that's where the actual change under test lives), via `/bin/bash -c`. Success emits `DeployMigrationCompleted` and moves on; failure emits `DeployFailed` immediately with captured stderr, which per [[004-Workflow]] §5 bounces the task back to `AwaitingPublish` rather than auto-retrying — **validated live**: a recipe accidentally mismatched to a different task's branch failed with a real Python traceback, correctly stayed at `AwaitingPublish`, and a corrected recipe then succeeded on retry. Each `restartTargets` entry (if any) then runs as its own shell command in the same directory, emitting `DeployRestartCompleted` per command or stopping at the first `DeployFailed`. Finally, `healthCheckUrl` (if set) is polled — `DeployHealthCheckPassed` or `DeployFailed` — before the overall `DeployCompleted`. See §2 for the trust gate (`Project.AllowAgentBypassPermissions`) this all sits behind, and for Forge's own self-hosted restart script.

## 4. Production Confirmation — Resolved via PR-Merge Polling, Not a Webhook

[[003-Domain]] row 10 (`PipelineConfirmedDeployment`) was an undesigned external event. **Resolved, founder-requested**: once a task reaches `Done`, `TaskWorkflow.RunAsync` polls the task's own `PullRequestUrl` (captured by `GitFinalizeAsync` right after `gh pr create`/`az repos pr create` succeeds — `AgentActivities.ExtractPrUrl`) every 60 seconds via `AgentActivities.CheckPullRequestMergedAsync`: `gh pr view <url> --json state` for GitHub (`state == "MERGED"`), `az repos pr show --id <id> --output json` for Azure DevOps (`status == "completed"`, PR ID parsed from the URL's `/pullrequest/{id}` segment). The moment it reports merged, the workflow sets `_productionConfirmed` itself and advances to `Production` — no human, no agent, no webhook.

This was chosen over a webhook receiver specifically because a webhook needs Forge's API reachable *from* GitHub/Azure DevOps — not true for a bare-metal/local deployment ([[ADR-0004]]). Polling the PR directly needs nothing incoming, only outbound CLI calls Forge already makes elsewhere (`GitOps`). The manual `ConfirmProductionAsync` signal ([[003-Domain]] row 10) still exists as a fallback for a task with no `PullRequestUrl` captured (an older task, or a push that never actually got a PR created for it).

## 5. Open Questions

- Exact storage shape for `PublishRecipe` (§2) once a second real project needs one — the JSONB-on-Project proposal above is a reasonable default, not a decision that's been stress-tested against a second use case.
- A worktree left behind after a refused (dirty) removal has no automatic detection/alerting — a human currently has to notice and clean it up manually, as happened during this validation.
- `restartTargets`/`healthCheckUrl` are implemented and validated against Forge's own self-hosted restart (§2) but not yet against a project with a genuinely separate, always-on service (Forge's own restart is closer to "relaunch a dev process" than "restart a deployed service").
- Forge changing its own `Forge.Workflows`/`Forge.Worker` code still needs a **manual** Worker restart after review (§2) — the self-restart script deliberately can't touch the process it's running inside of. Worth a real design pass (a tiny external supervisor? a two-phase restart signaled through a file/queue rather than in-process?) if this friction turns out to matter in practice, not before. §6 below covers how this constraint carries over (worse, in one respect) to the containerized topology.
- PR-merge polling (§4) checks every 60s indefinitely - no backoff, no giving-up condition. Fine at today's scale (a handful of tasks); revisit if this ever needs to scale to many concurrent `Done` tasks polling their own PRs.

## 6. Containerized Bring-Up (`docker compose`)

Founder-requested: let another developer clone the repo and run the whole stack — Postgres, Temporal, Temporal UI, Forge API, Forge Worker, and the Frontend — with one command, instead of the founder's own machine being a prerequisite (bare `dotnet run`/`vite` processes, `scripts/restart-forge-dev.sh`, `/home/felippe/...` paths).

**Setup**: `cp .env.example .env`, fill in the blanks (Postgres creds are fine at their defaults for local use; `FORGE_JWT_SECRET`, `GH_TOKEN`/`AZURE_DEVOPS_EXT_PAT` as needed, and `CLAUDE_CONFIG_DIR_HOST` are not), then `docker compose up -d`. No manual migration step — `Forge.Api`'s `Program.cs` runs `Database.MigrateAsync()` on startup (added alongside this containerization work) so a fresh Postgres volume ends up with a fully migrated `forge` schema before the API starts serving.

**What moved from hardcoded to environment-driven**: `FORGE_WORKTREES_DIR` (`AgentActivities.cs`) no longer defaults to `/home/felippe/forge-worktrees` — the fallback (used only if the env var is unset) is now the current user's profile directory, and the compose file always sets it explicitly to `/data/forge-worktrees`, backed by the `forge_worktrees_data` named volume. `FORGE_CORS_ORIGIN` is likewise now an env var (`Program.cs`) rather than a literal `http://localhost:5173`, though in the containerized topology it barely matters — the browser only ever talks to the frontend's own origin; nginx is what proxies `/api` to `forge-api` (see below), so no cross-origin request happens on the golden path at all.

**Frontend → API wiring**: `frontend/src/lib/api.ts`'s `BASE_URL = '/api'` and `useTaskWebSocket.ts`'s `location.host`-based WebSocket URL were already same-origin/relative (no `localhost:5080` baked into the built JS, verified by inspection before this work started). What was missing was something to make `/api` resolve to `forge-api` in a built, containerized frontend — the `frontend/Dockerfile` now serves the Vite build as static files from an nginx container, and `frontend/nginx.conf.template` proxies `location /api/` to `${FORGE_API_URL}` (nginx's `envsubst`-on-templates, official image behavior), defaulting to `http://forge-api:8080` — the Docker-network service name, not a host path. Changing which backend a given frontend container talks to is therefore a `FORGE_API_URL` env var on that container, not a rebuild.

**Worker image**: `backend/src/Forge.Worker/Dockerfile` installs `git`, `gh`, `az` (plus the `azure-devops` extension, required for `GitOps.RunAzAsync`'s `az repos` calls) and the Claude Code CLI (`@anthropic-ai/claude-code` via npm) at build time, so `GitOps.cs`/`ClaudeCliProvider.cs`'s bare `Process.Start("git"/"gh"/"az"/"claude", ...)` calls resolve from the image's own `PATH` instead of assuming the host machine has them. Credentials are supplied at container-start, never baked into the image:
- `GH_TOKEN` — a GitHub PAT; `gh` reads it natively, no `gh auth login` device flow needed headless.
- `AZURE_DEVOPS_EXT_PAT` — an Azure DevOps PAT; the `azure-devops` extension reads it natively, no `az login` needed. (Existing gap, unrelated to containerization: `CheckPullRequestMergedAsync`'s `az repos pr show` call, §4, doesn't pass `--organization`, so it still depends on whatever `az devops configure -d` default happens to be set — not something this env var fixes.)
- `CLAUDE_CONFIG_DIR_HOST` — a bind mount, not a token. Per [[ADR-0005]], Claude Code CLI auth is OAuth against a Claude.ai subscription, not an API key, so there's nothing to hand the container as a plain secret — the developer runs `claude` interactively once on some machine, then points this at that login's config directory (mounted into the container at `/root/.claude`, with `CLAUDE_CONFIG_DIR` set to match). Left unset, it defaults to an empty local `./data/claude-config` — deliberately non-fatal, same reasoning as `GH_TOKEN`/`AZURE_DEVOPS_EXT_PAT` above: the rest of the stack (board, API, everything short of an actual agent run) shouldn't refuse to start just because Claude Code isn't wired up yet. A Planner/Developer/Deploy activity run against that empty config dir fails with a clear "claude CLI reported an error" from `ClaudeCliProvider`, not a silent misbehavior.

**Project checkouts (`Project.LocalPath`)**: unchanged in shape, still a plain filesystem path read by the Planner/Developer activities — but that path now has to resolve *inside* the `forge-worker` container. `FORGE_REPOS_DIR` (host directory, defaults to `./data/repos`) is bind-mounted to `/data/repos` in the container; a project created via the UI should set `LocalPath` to `/data/repos/<checkout-folder-name>`, with the actual clone living at `<FORGE_REPOS_DIR>/<checkout-folder-name>` on the host.

**Self-hosting restart limitation: still present, now a different shape.** `scripts/restart-forge-dev.sh` (§1/§2's `pkill -f "dotnet run --urls ..."` / `pkill -f "vite --port ..."`) matches bare host processes — it has no matching process to find *inside* a container, and can't reach into the `forge-api`/`frontend` containers' process namespace from wherever it runs. If Forge's own dogfooded `Project.PublishRecipe.RestartTargets` is ever pointed at the containerized topology instead of the founder's bare-process dev setup, that entry needs to become something like `docker compose restart forge-api frontend` run from the host (or a host reachable over SSH), not this script — a data change to that Project's row, not a code change, so it's not made here without confirming which topology is actually driving self-hosting day-to-day. The deeper constraint the script encodes — **Forge.Worker can never restart itself**, since the restart would kill the process running the very Deploy activity performing it — is unchanged and, in fact, has no obvious fix in the containerized shape either: `docker compose restart forge-worker` from *inside* the `forge-worker` container would require mounting the Docker socket into it, which is a meaningfully larger trust boundary than a bash script killing a sibling process, and is not something this work adds. `Forge.Workflows`/`Forge.Worker` changes still need a manual `docker compose up -d --build forge-worker` after review, exactly as manual as the bare-process case's manual restart was.
