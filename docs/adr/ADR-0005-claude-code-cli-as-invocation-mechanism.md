# ADR-0005: Claude Code CLI (Interactive Auth) as the Agent Invocation Mechanism

## Status

Accepted

## Context

[[ADR-0003]] decided Forge's Model Router would ship with exactly one provider at v1 (Claude), but left open *how* that provider is actually invoked — the natural default assumption was a raw Anthropic Console API integration (an API key, direct SDK calls), which requires provisioning a separate API credential for Forge's own backend before any agent activity could run for real.

The founder pointed out an alternative: invoke the **Claude Code CLI itself** as a subprocess (`claude -p "<prompt>" --output-format ...`), authenticated via the interactive Claude.ai subscription login already present on the development machine (confirmed working — this exact mechanism already powers the local cron backstop in `scripts/cron-continue.sh`). This removes the separate-API-credential prerequisite entirely for single-account use, and it's arguably a more faithful reading of the founder's original scope: Forge was described from the start as orchestrating *Claude Code*, not a bespoke API integration built from scratch.

A related idea was raised: running multiple Claude accounts with automatic failover when one hits a usage limit. Investigated and confirmed technically feasible — Claude Code CLI respects a `CLAUDE_CONFIG_DIR` environment variable that isolates credentials/config per directory, independent of `$HOME` (verified: pointing `HOME` at an empty scratch directory produces a clean "not logged in" state, and the CLI binary itself references `CLAUDE_CONFIG_DIR` for exactly this kind of isolation). This means N accounts can coexist on one machine as N config directories, each logged in once.

## Decision

- Forge's agent activities (Planner, Developer, and eventually Deploy/Git where relevant) invoke the **Claude Code CLI as a subprocess** (`claude -p`, non-interactive/print mode), not the raw Anthropic API/SDK directly.
- **v1: single account by default.** The CLI uses whatever account is already logged in via the default `CLAUDE_CONFIG_DIR` (i.e., no override) on the machine running the Worker process, unless `CLAUDE_ACCOUNT_CONFIG_DIRS` is set (below).
- **Multi-account fallback: built (2026-08-08), founder-requested** — "o recurso de poder cadastrar multiplas contas do claude e ele reautenticar automaticamente para nunca parar o trabalho esta se tornando cada vez mais necessario." Went through two designs the same day:
  - **First attempt (reverted): `CLAUDE_CONFIG_DIR`-based accounts**, each a directory holding a full OAuth session. Technically correct (verified live, rotation worked against a fake `claude` binary) but the founder rejected the operational model outright — "nao gosto dessa estrategia de usar CLAUDE_CONFIG_DIR nao faz sentido na minha cabeca."
  - **What actually shipped: token-based accounts.** `claude setup-token` is a real Claude Code CLI subcommand ("Set up a long-lived authentication token, requires Claude subscription") that produces a single stable token string, consumed via the `CLAUDE_CODE_OAUTH_TOKEN` env var — confirmed present in the installed CLI binary's own strings (`strings` on the binary, not guessed or assumed from memory). This is the same UX shape as `Project.GitCredential` (paste a token, no directory/session management), which the founder had just approved for git auth minutes earlier — one consistent credential pattern across the app instead of two different ones.
  - `ClaudeAccount` (Domain entity, `docs/003-Domain.md`-style) — `Name`, `UserId` (linked to a Forge user, per "clicar no usuario e adicionar as contas vinculadas ao usuario"), `Token` (plaintext, `[JsonIgnore]`'d, same posture as `GitCredential`), `IsActive`. `ClaudeAccountPool.cs` queries active accounts fresh from Postgres each call (infrequent enough that caching would add complexity for no benefit) and tracks per-account cooldown in memory; `ClaudeCliProvider.InvokeAsync` tries each available account, and on a detected usage-limit failure (`ClaudeUsageLimitException`) marks it cooling down and rotates to the next. Zero-config default preserved: no `ClaudeAccount` rows at all falls back to whatever's already the ambient logged-in account, unchanged from before this existed.
  - **Real usage tracking, not just failover** — also founder-requested in the same message ("importante sempre a gente registrar quantos tokens gastamos por cada conta, qual a janela de limite que temos"): `Run.ClaudeAccountId` (nullable FK) records which account handled each invocation; `GET /users/{id}/claude-accounts` aggregates each account's `Run` rows into a rolling 5-hour session window and a rolling 7-day weekly window (cost, prompt/completion tokens, run count) — Forge's own estimate from its own recorded history, the same honest framing `GET /cost` already uses, since Anthropic exposes no API to query a subscription's actual remaining quota.
  - Verified live against a fake `claude` binary standing in for a real second account (no second real account exists yet to test against) — confirmed a rotation on the first call, and the exhausted account correctly skipped without a wasted attempt on the second.
  - **Still genuinely blocked on one thing only the founder can do**: each additional account needs `claude setup-token` run once, interactively, in his own terminal — producing the token he then pastes into Forge via "Add Claude account." Forge cannot generate this itself (it's a real, billable credential tied to his subscription).
  - **The usage-limit detection itself is unvalidated against a real failure** — `ClaudeCliProvider.IsUsageLimitError`'s phrase-matching is a best-effort guess at Anthropic's actual CLI wording, deliberately broad (over-matching costs one wasted rotation attempt; under-matching silently behaves like today). Worth tightening once a real usage-limit failure's exact text is observed live, the same honest bar [[015-Deployment]] applies elsewhere in this codebase.
  - **Known limitations, accepted for now**: cooldown state is in-memory, per-Worker-process — lost on a restart, and would need moving to Postgres if this ever ran as more than one Worker process (it doesn't today, [[007-ExecutionEngine]] §1). Live cooldown status also isn't surfaced via the API for the same reason — the Api and Worker are separate OS processes that don't share memory, so `GET /users/{id}/claude-accounts` shows usage *history* (from Postgres), not real-time account health.

## Consequences

- Removes the "Forge needs its own Anthropic API credential" blocker that had paused this build — the Planner/Developer agents can be implemented against a real LLM immediately, using the existing machine's login.
- Ties Forge's agent execution to whatever machine holds that CLI login and its usage limits/rate limits (a Claude.ai subscription's usage caps, not a Console pay-as-you-go pool) — acceptable for the founder's own single-machine development use per [[ADR-0004]], but this is a real constraint to revisit before any multi-user or higher-throughput scenario.
- Multi-account rotation, when built, spreads load across multiple *personal* subscription logins rather than a single scalable API billing account — this is a reasonable fit for a solo founder's own tool, but is a meaningfully different operational model from a typical SaaS backend's LLM billing, and is worth the founder independently confirming stays within Anthropic's usage policies for his account(s) before scaling past one.
- The `ClaudeCliProvider` becomes a subprocess-management concern (spawning `claude -p`, parsing its output, handling timeouts/kills) inside an Activity, not a simple HTTP client call — slightly more moving parts than a pure API integration, in exchange for zero additional credential provisioning.
- API-key-based providers (Console, or other vendors) remain a valid future `Provider` implementation for anyone who *does* want that model — this ADR doesn't foreclose it, it just isn't v1's path.
