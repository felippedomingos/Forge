# 012 — API

## Status

Draft — Phase 4 (Implementation)

## 1. Shape

.NET Minimal API, matching the "thin control plane" role from [[002-Architecture]] §1: every write endpoint below either starts/signals a Temporal workflow or performs a simple CRUD operation against [[011-Database]] — the API itself owns no lifecycle logic, that all lives in the Temporal workflows/activities ([[ADR-0001]], [[004-Workflow]], [[005-Agents]]).

## 2. REST Endpoints (v1)

| Method | Path | Behavior |
|---|---|---|
| `POST` | `/auth/bootstrap` | Creates the first `Admin` User and returns a JWT. `403` the instant any User row already exists — functions exactly once, ever ([[adr/ADR-0006]]). |
| `GET` | `/auth/needs-bootstrap` | `{needsBootstrap: bool}` — whether zero Users exist yet, so the frontend knows whether to show the bootstrap form or a plain login form. |
| `POST` | `/auth/login` | Email + password (`BCrypt` verify) → a JWT (24h expiry, no refresh token - [[adr/ADR-0006]]). `401` on no match. |
| `POST` | `/users` | Create a User (Admin-only — `403` unless the caller's `role` claim is `"Admin"`). No public signup endpoint exists. |
| `GET` | `/users` | List Users (id/name/email/role only, never a password hash). Admin-only. |
| `GET` | `/projects` | List all Projects. |
| `POST` | `/projects` | Create a Project (repository URL, root branch, git provider plugin config, `prefix` for task tags, optional `allowAgentBypassPermissions` — defaults `false`). |
| `GET` | `/projects/{id}` | Single project detail — backs the sidebar's edit view ([[013-Frontend]]). |
| `PATCH` | `/projects/{id}` | Edit `name`/`repositoryUrl`/`rootBranch`/`localPath`/`allowAgentBypassPermissions`. `prefix` is deliberately not editable here — it's immutable once any Task references it in a tag ([[003-Domain]] §1). |
| `DELETE` | `/projects/{id}` | Deletes the Project; cascades at the DB level to every Task/SubTask/AcceptanceCriterion/Run/Event/Worktree/AgentMemory under it ([[011-Database]] - all FKs below Project are `DeleteBehavior.Cascade`). Also best-effort terminates the project's `BacklogSchedulerWorkflow` and every task's `TaskWorkflow` ([[006-Scheduler]]) so deleting a project doesn't leave orphaned Temporal executions polling/parked forever - "best-effort" because a workflow already completed or never started isn't a failure worth blocking the delete over. |
| `GET` | `/projects/{id}/memory` | List the project's shared `AgentMemory` entries ([[005-Agents]] §7). |
| `PUT` | `/projects/{id}/memory` | Upsert a shared memory entry by `key`. |
| `DELETE` | `/projects/{id}/memory/{key}` | Remove a shared memory entry. |
| `GET` | `/tasks` | List Tasks, filterable by `project_id` and `state` — backs the cross-project board view ([[000-Vision]] UC-1), which doubles as the founder-requested "all tasks across all projects" view. |
| `POST` | `/tasks` | Create a Task with a `title` (per [[000-Vision]] UC-3) and an optional `description` — user-provided seed notes (may include a URL; see [[005-Agents]] §2 on how the Planner uses it) that the Planner's own output overwrites once it finishes. Starts the Task's Temporal workflow, which immediately begins in `Inbox`. Assigns the task's `number` from `Project.NextTaskNumber` atomically in the same save, so its tag (`{Project.Prefix}-{number}`) is stable and collision-free. |
| `GET` | `/tasks/{id}` | Full task detail: description, acceptance criteria, sub-tasks, current state, active `Run`, worktree/branch info. |
| `POST` | `/tasks/{id}/move` | Human-driven state transition (`Blocked→Inbox`, `AwaitingPublish→Publishing`, `Review→Done`) — translates to a Temporal Signal against that task's workflow ([[002-Architecture]] §2). Rejected with `409` if the requested transition isn't a legal edge for the task's current state ([[003-Domain]] INV-3). |
| `POST` | `/tasks/{id}/answers` | Submit answers to a `Blocked` task's open questions — a specialized case of `/move` with a payload, kept as its own endpoint since the answers themselves are meaningful data, not just a state change. |
| `GET` | `/tasks/{id}/runs` | List `Run` rows for a task — the agent invocation history. |
| `GET` | `/tasks/{id}/events` | The task's `events` timeline ([[011-Database]]) — backs the UI timeline view. |
| `GET` | `/workers` | *(Not implemented)* List Worker status (`idle`/`busy`/`offline`) and current task assignment. |
| `GET` | `/plugins` | List configured Plugins ([[010-Plugins]]) — backs the new-project dialog's git-provider picker ([[013-Frontend]]). |
| `GET` | `/git/branches?repositoryUrl=` | Lists a repository's actual branches (`git ls-remote --heads`) — founder-requested, replaces a guessed `main`/`develop`/`dev` list in the project create/edit dialogs' Root branch field ([[013-Frontend]]). Provider-agnostic by construction (talks to the git remote directly, not a GitHub/Azure DevOps API), and not scoped to an existing Project - called before one exists, during creation. `400` with the git error on an unreachable/invalid URL. |
| `GET` | `/tasks/{id}/cost` | Rolled-up token usage and cost estimate for a task, from its `Run` rows ([[008-ModelRouter]] §5). |
| `GET` | `/cost` | Same rollup, global across every project — backs the founder-requested spend indicator in the sidebar. **Not a real account-level quota**: agents run through the Claude Code CLI under interactive subscription auth ([[adr/ADR-0005]]), which exposes no "usage remaining" API; this is `Run.CostEstimate` summed, itself an estimate against Anthropic's API list price, not what the subscription actually bills. |
| `POST` | `/tasks/{id}/promote` | Manual override of [[006-Scheduler]]'s `BacklogSchedulerWorkflow` — harmless to call since it guards on `state==Backlog`. Useful for tests/demos. |
| `POST` | `/tasks/{id}/request-replan` | Founder-requested ([[004-Workflow]] row 15) — sends a `Backlog` task back to `Inbox` for a fresh `PlanAsync` pass, e.g. when the write-up itself needs a rewrite before any Developer work starts. Signals `RequestReplanAsync`, guarded on `state==Backlog` same as `/promote`. |
| `POST` | `/tasks/{id}/resume` | Starts a fresh `TaskWorkflow` for a Task whose workflow never ended up driving it — either the documented `POST /tasks` gap (row insert and `StartWorkflowAsync` aren't one transaction; a crash or Worker outage between the two orphans the row) or a workflow that terminally `Failed` and won't retry itself. `409` if a workflow is already running for this task (Temporal's default `WorkflowIdReusePolicy` refuses to double-start over an open execution) — safe to call speculatively on anything that looks stuck. **Found and fixed live**: two tasks were discovered stuck in `Inbox` with zero events — one from a stale Worker process still running pre-fix `PostgresNotify` code that failed `PersistTaskStateAsync` outright, the other from the exact row/workflow race this endpoint exists for. Both recovered via this endpoint (confirmed via Temporal's own workflow history, not just the DB row) rather than being re-created from scratch. **Also the mechanism for a task with no workflow *and* a real, already-curated `Description`** (e.g. the SlayZone import, [[016-Roadmap]] - 252 tasks inserted directly into Postgres, deliberately bypassing `POST /tasks`/`StartWorkflowAsync` to avoid triggering the Planner on import): calling this with `Task.State == Backlog` starts `TaskWorkflow.RunAsync` with `resumeFrom: Backlog`, which skips `PlanAsync` entirely on its first pass (see `TaskWorkflow.cs`'s `skipPlanningOnce`) rather than overwriting that description with a fresh Planner run - the task goes straight to waiting for a promotion signal. |
| `POST` | `/tasks/{id}/request-changes` | `{comment}` — founder-requested: sends a `Review`-stage task back to `Todo`/`Executing` for another Developer pass instead of only approving ([[004-Workflow]] row 14, §3a). The comment is recorded as a `ReviewRequestedChanges` event and read by the next `DevelopAsync` run. |
| `POST` | `/tasks/{id}/confirm-production` | Manual escape hatch for `ConfirmProductionAsync` ([[003-Domain]] row 10) - the signal existed on `TaskWorkflow` but nothing exposed it over HTTP until found missing live (2026-08-06). For a `Done` task with no `PullRequestUrl` captured (predates that field, or a push that never got a PR) - the automatic PR-merge poll ([[015-Deployment]] §4) has nothing to check without a URL, so this is the only way such a task ever reaches `Production`. |
| `POST` | `/projects/{id}/resume-scheduler` | Same recovery as `/tasks/{id}/resume`, for a Project's `BacklogSchedulerWorkflow` ([[006-Scheduler]]). `409` if already running. **Found and used live**: a scheduler that had run ~19h at its 5s poll interval hit Temporal's history size limit and was terminated by the server before `Workflow.ContinueAsNewSuggested` (the actual fix) existed - this endpoint recovered it without losing the project's scheduling state. |
| `GET` | `/health` | `{"status":"healthy"}`, unauthenticated. Exists specifically so a `PublishRecipe.healthCheckUrl` pointing at Forge's own API has something to poll that isn't rejected by the global auth policy (§4 below). |
| `PATCH` | `/projects/{id}/publish-recipe` | Configure a Project's `PublishRecipe` ([[015-Deployment]] §2), including `previewUrl` (the founder-requested "Testar" button's target). Replaces the whole recipe — callers must round-trip fields they don't want cleared. |

No `/agent/execute` endpoint exists — agents are never invoked directly by an API call; they only run as Temporal activities scheduled by a workflow reacting to a state transition. An endpoint that could directly trigger an agent would bypass the state machine entirely, which [[003-Domain]] INV-3 exists specifically to prevent.

## 3. WebSocket Channel

**Implemented**: `/ws/tasks/{id}`, one connection per task, backed by `TaskEventBroadcaster` + `PostgresNotificationListener` — see [[007-ExecutionEngine]] §4 for the full mechanism (Postgres `LISTEN`/`NOTIFY` bridging the Worker process to the API's in-memory connections). Each message is a minimal `"refresh"` string, not the actual event data — clients re-fetch `GET /tasks/{id}` and `/tasks/{id}/events` on receiving it. This is the data source for [[000-Vision]] UC-9 and the task detail panel in [[013-Frontend]], validated live with real sub-second delivery.

## 4. AuthN/AuthZ

**Implemented** ([[adr/ADR-0006]], [[014-Security]] §1): JWT bearer tokens, checked via ASP.NET Core's default-deny fallback authorization policy — every endpoint above requires a valid, unexpired token except `/auth/login` and `/auth/bootstrap`. AuthZ is a single coarse check (`role == "Admin"` gates `POST/GET /users`), not a per-project or per-action permission matrix — no product requirement for finer-grained roles exists yet.

The WebSocket endpoint (§3) can't receive a custom `Authorization` header from a browser's native `WebSocket` API, so it accepts the token as `?access_token=` instead, validated the same way via `JwtBearerEvents.OnMessageReceived`.

## 5. Versioning Policy

Not yet needed — there are no external consumers of this API besides Forge's own frontend, versioned and deployed together. Revisit if/when a third-party or a separate frontend build needs API stability guarantees independent of the backend's own release cadence.
